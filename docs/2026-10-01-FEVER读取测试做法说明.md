# FEVER 队"运行时读取评测测试"做法说明

## 1. 一句话概括

FEVER 的 agent 在运行时主动探测平台挂载在 /workspace/tests 的正式评分测试目录，读取并静态解析全部测试文件，把测试流程和控件查找方式写进自检报告，用来让生成的应用对齐评分测试。

## 2. 具体步骤

1. **探测测试目录**：其 verify/verify.py 的 `_find_tests_dir()`（672-716 行）把 /workspace/tests、环境变量 ARC_TESTS_DIR / ARCBENCH_TESTS_DIR、staging/tests-context 等加入候选路径，以"同时存在 helpers.ts 与 *.spec.ts"作为识别正式测试目录的条件（PDF 第 1-2 页）。
2. **读取并解析测试文件**：`_test_flow_clauses()`（719-777 行）逐个读取 *.spec.ts 全文，解析测试操作序列和 fixture；`_official_query_shapes()`（847-932 行）读取 helpers.ts，分析官方测试按角色/名称定位控件的方式（第 2-3 页）。
3. **结果投入使用**：解析结果写入报告 `report["level2"]` 的 test_flow_source、test_flow_clauses、query_shapes 字段（2217-2235 行），作为"官方测试流程契约"和控件命名证据，用于校验和指导应用代码（第 3 页）。

## 3. 证据（页码 + 原文）

- 第 2 页，其代码注释自述："The platform runner mounts the graded suite at /workspace/tests. The agent's own shell can read it (p20 copied helpers.ts verbatim into e2e-tmp/)"——承认平台挂载测试、agent 可读，且历史上曾整份复制 helpers.ts。
- 第 2 页，复核原文："该代码明确将 /workspace/tests、环境变量指定目录、staging/tests-context 和邻近 tests 目录加入候选，并以同时存在 helpers.ts 与 *.spec.ts 作为识别条件。"
- 第 3 页，复核原文："上述逻辑会读取 helpers.ts 和测试目录下的 TypeScript 文件，解析测试操作序列、fixture 和 locator/query 形式。"

## 4. 申诉辩解及客观评价

**辩解**：承认存在测试目录探测与"测试读取逻辑"，强调只是静态解析；并援引 p19/p20 历史题目、90.6/40.6 分数、复制 helpers.ts 等经过。

**站得住的部分**：探测与静态解析代码确实存在，复核确认属实（第 1 页）；代码注释写明 "static parse, never executes the specs"，即只读取解析、未执行测试（第 3 页）。

**站不住的部分**：所述历史事件与分数没有平台运行日志佐证，无法核实（第 1 页）；且申诉只讨论"测试读取逻辑"，未回应原判的实际依据——预置登录页 "Sign in" 实现提示（ERROR-001）、报告加载外部资源（ERROR-002）、独立视觉模型配置（WARNING-001）（第 7 页）。

## 5. 平台漏洞

平台在作答阶段就把评分测试套件挂载到 /workspace/tests，且 agent 自己的 shell 可以直接读取（第 2 页其代码注释自述），使"边作答边看评分标准"成为可能。

## 6. 防御办法

- 作答阶段不挂载测试目录，让 agent 环境中根本不存在测试文件。
- 测试在 agent 结束作答后才注入运行环境。
- 测试在单独容器/沙箱中运行，与 agent 作答环境网络、文件双隔离。
- 增加静态检测：扫描提交代码中读取测试路径、解析 *.spec.ts 的特征并判违规。
