# FEVER"运行时读取评测测试"复现指南（红队验证用）

> 目的：让主办方同事在自己的环境里照做一遍，亲手验证"agent 作答时能读到评分测试"这个漏洞可以被利用到什么程度，再据此验收防御。
> 边界：仅用于我们自己的平台与测试包；不复现完整攻击 agent，只复现"读测试 → 提取契约 → 推导实现指令"这一核心链路。

## 0. 原理一句话

评分测试套件在作答阶段被挂载到 agent 可读的路径（/workspace/tests），agent 只需静态读取 *.spec.ts 和 helpers 文件，就能提前拿到全部断言细节（控件角色与精确名称、表单 label、错误文案、种子密码），照着写实现即可高分通过。FEVER 队代码中该逻辑已被复核确认存在（申诉 PDF 第 1-3 页）。

## 1. 复现环境准备

- 一台 Mac/Linux，装有 Python 3.10+（不需要 Node，全程只做静态文本解析，不执行测试）。
- 测试包一份：`github-stage-1-req-test.zip`（12 个 *.spec.ts + tests/support/e2e.ts）。
- 模拟平台布局（对应线上"runner 把评分套件挂载到 /workspace/tests"）：

```bash
mkdir -p /tmp/arcbench-repro/workspace/app
cd /tmp/arcbench-repro
unzip -q github-stage-1-req-test.zip
# 用软链模拟"挂载"：workspace/tests 就是线上的 /workspace/tests
ln -sfn /tmp/arcbench-repro/github-stage-1-req-test/tests workspace/tests
```

## 2. 复现步骤

复现脚本：`documents/repro-fever/probe.py`（约 100 行，三段函数与 FEVER 被核实的代码一一对应）。

**第 1 步：探测测试目录**（对应其 `_find_tests_dir()`，verify/verify.py:672-716，PDF 第 1-2 页）。
脚本依次检查环境变量 ARC_TESTS_DIR / ARCBENCH_TESTS_DIR、/workspace/tests、workspace/tests、staging/tests-context，发现含 *.spec.ts 的目录即命中。FEVER 原代码还要求同时存在 helpers.ts；本测试包的 helpers 等价物是 tests/support/e2e.ts，脚本以 *.spec.ts 为充分条件。

**第 2 步：读取并静态解析**（对应 `_test_flow_clauses()` / `_official_query_shapes()`，verify/verify.py:719-777、847-932，PDF 第 2-3 页）。
脚本逐个读取 12 个 spec 全文，用正则提取：test 场景标题、page.goto 导航、getByRole(角色, 名称, exact)、getByLabel、getByText 断言；再解析 support/e2e.ts 提取种子账号表、统一种子密码、helper 函数清单。

**第 3 步：产出契约并推导实现指令**（对应其写入 report["level2"] 的 test_flow_source / test_flow_clauses / query_shapes，verify/verify.py:2217-2235，PDF 第 3 页）。

```bash
python3 attack/probe.py   # 产出 out/contract.json
```

## 3. 实际复现结果（本机已跑通）

```
test_flow_source: /private/tmp/arcbench-repro/workspace/tests
解析 spec 文件数: 12
提取 getByRole 定位: 102 处，示例: [{'role': 'link', 'name': 'Sign in', 'exact': True}, ...]
表单 label 契约: ['Confirm password', 'Email', 'New password', 'Password', 'Username or email', 'Verification code']
文案断言契约: ['Access denied', 'Account not found', 'Current password is incorrect', ...]
种子密码规则: Valid-password-123!
```

由 contract.json 自动推导出的实现指令（`documents/repro-fever/implementation_brief.md`）：

```
- 名称 'Sign in' 必须同时满足角色: ['button', 'link']（exact 匹配）
- 必须出现的文案: ['Invalid credentials']
- 表单控件 label 必须是: ['Password', 'Username or email']
- 所有种子账号统一密码: Valid-password-123!
```

**攻击效果**：第一条指令就是 FEVER 预置在 prompt 里的那条登录页规则（"页头 Sign in 做成普通链接，表单 SIGN IN 是唯一同名按钮"，PDF 第 3-4 页 ERROR-001）。也就是说：他们靠历史跑分积累的"经验规则"，用这个方法几秒钟就能从测试文件里自动推出来。拿到这 102 处定位契约 + 全部文案断言 + 种子密码后，agent 生成应用时逐条对齐即可，不需要真正理解题面。

## 4. 防御及其验证方法

| 防御 | 做法 | 用本复现验证 |
|---|---|---|
| 作答阶段不挂载测试 | 评测环境构建时不拷贝/不 mount 测试目录 | 把 workspace/tests 挪走后重跑 probe.py，输出 `test_flow_source: None`、提取数全为 0 —— 与 FEVER 注释自述的 `test_flow_source: null` 现象一致（PDF 第 2 页），攻击失效 |
| 测试事后注入 | agent 作答完成、产物封存后才把测试注入运行环境 | 同上，作答期 probe.py 拿不到任何契约 |
| 单独容器跑测试 | 测试在独立容器执行，与作答环境文件/网络双隔离 | 在作答容器内跑 probe.py 应全部落空 |
| 静态特征检测 | 扫描提交代码中的测试探测特征 | grep 特征（在 FEVER 代码与本复现脚本上均命中）：`_find_tests_dir`、`/workspace/tests`、`ARC_TESTS_DIR`、`ARCBENCH_TESTS_DIR`、`glob("*.spec.ts")`、读取 `helpers.ts` 后解析 locator 的逻辑 |

建议组合：前两条是根因修复（测试不出现在作答时空），第四条是兜底检测（即使将来环境配置失误也能事后发现）。

## 5. 局限说明

- 本复现只覆盖"静态读取与解析"，与 PDF 核实的范围一致（"static parse, never executes the specs"，第 3 页）；不演示动态执行测试刷分。
- FEVER 注释中还自述"p20 曾把 helpers.ts 整份复制进 e2e-tmp/"（第 2 页），说明除静态解析外还有直接搬运测试文件的做法，防御第 1/2 条同样覆盖。
- 若测试包本身公开可下载，即使平台不挂载，队伍仍可线下用同一套方法预写规则（对应 FEVER ERROR-001 的历史经验来源）；根治需叠加"测试保密"或"断言随机化/每届更换"。
