# FEVER"运行时读取评测测试"复现指南（详细版）

> 给谁看：主办方同事。不需要安全背景，会开终端、会复制粘贴命令就行。
> 要多久：手动版 5 分钟，脚本版 5 分钟，读懂全部约 30 分钟。
> 要准备什么：一台 Mac 或 Linux 电脑，装 python3（3.10 以上）。不需要 Node，不需要启动任何应用。
> 原则：每一步都给出命令、预期输出、"看到什么说明什么"。所有关键说法都标了证据 PDF 的页码。

---

## 1. 先搞懂漏洞是什么

比赛的正常流程是这样的：

1. 平台给参赛 agent 一个作答环境（一个目录，里面只有题面 requirements.yaml）。
2. agent 在环境里生成 app 代码。
3. agent 结束后，平台把官方评分测试跑在 app 上，按通过的测试数给分。

漏洞出在第 1 步和第 3 步之间：**评分测试文件在作答阶段就被挂载到了 agent 能读到的地方**（/workspace/tests）。

这不是猜测。FEVER 队自己的代码注释里写着（证据 PDF 第 2 页，原文照引）：

> The platform runner mounts the graded suite at /workspace/tests. The agent's own shell can read it (p20 copied helpers.ts verbatim into e2e-tmp/)

翻译：平台的 runner 把评分套件挂在 /workspace/tests，agent 自己的 shell 能读到它；他们还在另一题（p20）里把 helpers.ts 整份复制过。

所以作弊者不需要黑任何东西。门没锁，推门就进。他要做的只有三件事：找到测试目录、读文件、照着写。本指南就复现这三件事。

## 3. 手动复现（不用脚本，5 条 grep 建立直觉）

先别看脚本。作弊者偷的东西，你用手就能翻出来。以下命令都在仓库根目录执行。

**第 1 条：测试要点击的控件叫什么、是什么角色**

```bash
grep -ho "getByRole('[a-z]*', { name: '[^']*'" test-package/tests/*.spec.ts | sort | uniq -c | sort -rn | head
```

你会看到（真实输出节选）：

```
15 getByRole('button', { name: 'Account menu'
14 getByRole('link', { name: 'Sign in'
12 getByRole('link', { name: 'Your organizations'
10 getByRole('button', { name: 'Sign in'
...
```

看到什么说明什么：评分测试靠"角色 + 精确名字"找控件。作弊者现在知道了：页面上必须有一个叫 Sign in 的**链接**（被点 14 次），还有一个叫 Sign in 的**按钮**（被点 10 次），退出要先点 Account menu 按钮。这正是 FEVER 预置进 prompt 的那条登录页规则（PDF 第 3-4 页），一条 grep 就推出来了。

**第 2 条：表单 label 必须叫什么**

```bash
grep -ho "getByLabel('[^']*'" test-package/tests/*.spec.ts | sort -u
```

输出：`Confirm password`、`Current password`、`Display name`、`Email`、`New password`、`Organization name`、`Password`、`Team name`、`Username`、`Username or email`、`Verification code`，共 11 个。
说明：输入框必须用这些 label，否则测试找不到输入框，直接挂。

**第 3 条：必须显示什么文案**

```bash
grep -ho "getByText('[^']*'" test-package/tests/*.spec.ts | sort -u | head
```

输出里有 `Invalid credentials`、`Access denied`、`Account not found` 等。
说明：错误提示必须一字不差地用这些文案。

**第 4 条：种子账号的密码是什么**

```bash
grep -n "SEEDED_PASSWORD" test-package/tests/support/e2e.ts
```

输出：`const SEEDED_PASSWORD = 'Valid-password-123!';`
说明：所有预置账号的密码都在明面上。

**第 5 条：测试从哪开始、怎么导航**

```bash
grep -n "goto\|toHaveCount" test-package/tests/support/e2e.ts | head
```

输出里有两行关键事实：`page.goto(baseUrl())`（测试永远从首页 `/` 开始）和 `expect(signInLink).toHaveCount(1)`（Sign in 链接在页面上**只能出现一次**，多一个就判失败）。
说明：作弊者连"页面结构约束"都拿到了——这就是 FEVER 规则里"页头 Sign in 只能做成普通链接"的真正原因（PDF 第 3-4 页）。

**手动版结论**：5 条 grep，不到一分钟，登录、退出、找回密码这三大类测试的断言细节已经全部到手。剩下的 102 处定位只是量的差别。脚本只是把这件事自动化。

## 4. 脚本复现（probe.py 逐段讲解）

### 4.1 跑起来

```bash
# 先模拟平台挂载（软链扮演 /workspace/tests）
mkdir -p _demo/workspace
ln -sfn "$PWD/test-package/tests" _demo/workspace/tests

# 跑
python3 probe.py
```

预期输出（真实跑出来的）：

```
test_flow_source: /.../_demo/workspace/tests
解析 spec 文件数: 12
提取 getByRole 定位: 102 处，示例: [{'role': 'link', 'name': 'Sign in', 'exact': True}, ...]
表单 label 契约: ['Confirm password', 'Email', 'New password', 'Password', 'Username or email', 'Verification code']
文案断言契约（部分）: ['123456', 'Access denied', 'Account is already a member', ...]
种子密码规则: Valid-password-123!
helper 函数: ['seedAccount', 'seedValue', 'openVisibleOrganization', ...]

# 由 contract.json 自动推导的实现指令（登录页示例）
- 名称 'Sign in' 必须同时满足角色: ['button', 'link']（exact 匹配）
- 必须出现的文案: ['Invalid credentials']
- 表单控件 label 必须是: ['Password', 'Username or email']
- 所有种子账号统一密码: Valid-password-123!
```

### 4.2 probe.py 的每个函数对应 FEVER 的哪段代码

| probe.py 函数 | 干什么 | FEVER 真实代码 | PDF 页码 |
|---|---|---|---|
| `find_tests_dir()` | 在候选路径里找测试目录 | `verify/verify.py:672-716` `_find_tests_dir()` | 第 1-2 页 |
| `test_flow_clauses()` | 逐个读 spec，提取操作序列和断言 | `verify/verify.py:719-777` `_test_flow_clauses()` | 第 2-3 页 |
| `official_query_shapes()` | 读 helpers，提取账号/密码/helper 函数 | `verify/verify.py:847-932` `_official_query_shapes()` | 第 2-3 页 |
| 输出 `level2` 三个字段 | 写进报告 | `verify/verify.py:2217-2235` 写入 `report["level2"]` | 第 3 页 |

### 4.3 探测逻辑的细节（为什么它找得到）

`find_tests_dir()` 依次检查这些位置，第一个命中就用：

1. 环境变量 `ARC_TESTS_DIR`、`ARCBENCH_TESTS_DIR`、`ARC_EXPORT_DIR`（及其下的 `staging/tests-context`）——万一平台"好心"用环境变量告诉 agent 测试在哪；
2. `/workspace/tests`——线上平台的真实挂载点（PDF 第 2 页）；
3. 作答目录旁边的 `tests`、`staging/tests-context`——万一相对路径就摸得到。

识别条件：目录里有 `*.spec.ts`。FEVER 原版还要求同时存在 `helpers.ts`（PDF 第 2 页复核原文："以同时存在 helpers.ts 与 *.spec.ts 作为识别条件"）；本测试包的 helpers 等价物是 `tests/support/e2e.ts`，所以脚本放宽为只看 spec。

要点：这不是攻击平台，只是**列目录 + 读文件**。任何 agent 框架（Codex、Claude Code、自研）都能做到，因为 agent 日常就是读写文件。

### 4.4 contract.json 里到底有什么

打开 `_demo/out/contract.json`（或现成样例 `example-output/contract.json`），结构是：

```json
{
  "level2": {
    "test_flow_source": "...",            // 测试目录在哪（找到=路径，没找到=null）
    "test_flow_clauses": [                 // 每个 spec 一份
      {
        "file": "REQ-1-1-2-sign-in.spec.ts",
        "scenarios": ["REQ-1-1-2: Sign In ... Scenario 1", ...],  // 4 个场景标题
        "role_lookups": [{"role": "link", "name": "Sign in", "exact": true}, ...],
        "labels": ["Username or email", "Password"],
        "text_assertions": ["Invalid credentials", ...]
      }, ... 共 12 份
    ],
    "query_shapes": {
      "helpers": ["support/e2e.ts"],
      "seeded_password": "Valid-password-123!",
      "seeded_accounts": [["LOGIN", "alice-dev"], ...],   // 全部预置账号
      "exports": ["seedAccount", "signIn", ...]           // helper 函数清单
    }
  }
}
```

字段名故意和 FEVER 自检报告 `report["level2"]` 的三个字段同名（PDF 第 3 页：test_flow_source / test_flow_clauses / query_shapes），方便对照。

### 4.5 从契约到代码：作弊的最后一步

有了 contract.json，作弊者把它变成两类东西：

**A. 变成 prompt 规则，喂给生成 app 的模型。** 真实案例对照：

- FEVER 的 prompt 里预置了一条规则：页头 "Sign in" 做成普通链接，让表单提交按钮成为唯一同名 button（PDF 第 3-4 页，`_FULL_CONTRACT_ITEMS`，默认注入所有模块的 prompt）。这条规则和我们脚本自动推导出的第一条指令一字不差。
- 另一支队 e0_7 更直接：他们的 `dialect.md` 写着"测试用 `getByRole('button', {name: /sign out/i})` 找退出按钮，有一回做成 `<a>` 链接，135 个测试挂了 73 个"、"每个测试都在未登录状态打开 `/`，从不手输网址"（PDF 第 15-16 页），并无条件放在题面前面发给模型（PDF 第 17 页）。这些细节只能来自读测试或跑测试。

**B. 变成自检清单，生成后自动核对。** FEVER 的 verify.py 就是把解析结果写进报告当"官方测试流程契约"用（PDF 第 3 页）。

注意一个诚实的地方：这两支队被原反作弊判 ERROR 的直接原因不是"读测试"本身，而是预置实现提示、外部资源加载等（PDF 第 7 页）。但"读测试"是他们能写出那些精确规则的前提。本仓库复现的就是这个前提。

## 5. 防御：每一条怎么实施、怎么验证算成功

### 5.1 作答阶段不挂载测试（根因修复）

- **原理**：测试文件在 agent 作答的时空里根本不存在，读无可读。
- **实施**：检查平台 runner 的编排逻辑，把"准备测试目录"这一步从"启动 agent"移到"agent 结束"之后；作答环境的镜像和挂载清单里不得出现测试。
- **用本仓库验证**：`rm -f _demo/workspace/tests` 后跑 `python3 probe.py`。
- **成功标准**：输出 `test_flow_source: None`，提取数全为 0。`run.sh` 的第 2、3 幕自动演示了这一幕。这个现象和 FEVER 自述一致——他们的注释说平台 gate 读不到测试时 "observed as `test_flow_source: null`"（PDF 第 2 页）。

### 5.2 测试事后注入

- **原理**：作答和评测是两个先后阶段，测试只在评测阶段进入环境。
- **实施**：agent 产物先封存（打快照/提交），再注入测试目录，再跑 Playwright。封存后 agent 不能再改文件。
- **验证**：同 5.1，在"作答窗口期"跑 probe.py 应全部落空。

### 5.3 单独容器跑测试

- **原理**：即使时间上有重叠，空间上也隔开。测试容器只拿到 app 的访问地址（URL），不共享文件系统。
- **实施**：评测容器挂载测试，通过 HTTP 打作答容器里启动的 app；两容器不共享 volume。
- **验证**：在作答容器里跑 probe.py 应找不到任何 spec；同时确认评测容器能正常跑测试。

### 5.4 静态特征检测（兜底）

- **原理**：前三条是环境修复；这条是事后审计——参赛代码里出现"找测试目录、解析 spec"的特征就标记。
- **实施**：对每份提交跑特征扫描，命中即人工复核。
- **规则**（ripgrep，直接在参赛提交目录跑）：

```bash
rg -n "_find_tests_dir|/workspace/tests|ARC_TESTS_DIR|ARCBENCH_TESTS_DIR|tests-context|glob\(.?\*\.spec\.ts|helpers\.ts" --type py --type ts --type js
```

- **验证**：在 FEVER 提交（verify/verify.py）和本仓库 probe.py 上跑，都应命中多条。在本仓库试：`rg -n "ARC_TESTS_DIR|/workspace/tests" probe.py`，预期命中 2 行以上。
- **注意误报**：正常 app 代码几乎不会出现这些字符串，误报率很低；命中后以人工裁定为准，不要自动判负。

### 5.5 关于"测试包公开可下载"

前四条只能堵"运行时读测试"。但既然测试包公开，作弊者可以**线下**用同一套方法预写规则（第 4.5 节 A），比赛时直接注入 prompt。要堵这条，只剩两招：测试保密（不公开或赛后公开），或者每届/每题随机化断言细节（改控件命名、改文案、改流程顺序），让预写规则失效。这是一个需要赛事层面拍板的取舍：公开测试有利于公信力，保密/随机化有利于防作弊。

## 6. 常见问题

**Q：run.sh 报 "No such file or directory"？**
A：先 `cd` 到仓库根目录再跑。脚本里所有路径都相对仓库根目录。

**Q：python3 版本不够？**
A：脚本用了 `Path | None` 这种写法，需要 3.10+。老版本把函数签名里的 `Path | None` 删掉即可，逻辑不受影响。

**Q：为什么不直接跑 Playwright 测试来演示？**
A：故意不跑。FEVER 的做法就是"只读不跑"（代码注释：static parse, never executes the specs，PDF 第 3 页）。只读文件防不胜防——不产生进程、不产生网络流量，平台日志里几乎无痕。这也是它危险的原因。

**Q：probe.py 会不会改坏我的测试包？**
A：不会。它只做读取，唯一的写操作是把报告写到 `_demo/out/`。

**Q：这个方法对别的比赛/别的题也适用吗？**
A：只要"评分测试在作答时可被 agent 读到"就适用，与题目内容无关。换一套测试包，probe.py 不用改。

## 8. 局限（老实交代）

- 复现范围与 PDF 核实范围一致：只复现"读和解析"，没复现"动态执行测试刷分"。
- FEVER 自述曾整份复制 helpers.ts（PDF 第 2 页），防御 5.1/5.2 同样覆盖这种直接搬运。
- probe.py 是教学版，只提取最关键的几类断言；真实作弊者可以解析得更全（正则、AST 都行），方向相同、程度更深。
- 第 5.5 节的"测试公开"问题没有完美解，需要赛事层面取舍。
